## 1. Verdict

Both halves do what their briefs say. The newest-request-wins rule in `PlayRequest.js` is right: `play-info` is not a job command, so each request spawns its own process and the purpose id can never be overwritten by `JobQueue.enqueue`'s re-tagging (which only applies to queued job commands). Removal and Stop drop an in-flight request, and a reply for a removed book is ignored. B14's staged build is sound: everything is written and probed inside `.partial/`, renames are same-filesystem, and `ffprobe` runs on the staged temp name with no key.

Two findings deserve a task; the rest are hygiene. F34 is a logic regression introduced by combining F10 with F7 and is worth fixing before the next real re-download.

## 2. Findings

Severity: **M** fix soon, **L** when touching the file.

| # | Sev | Owner | Finding |
|---|---|---|---|
| F34 | M | backend (B14) | **Free-space pre-flight over-counts on a re-download.** `_reclaimable_bytes` (`download.py:233`) adds the old audio's size to free space, and ARCHITECTURE §4.3 step 1 now says so. But since B14 the old copy stays on disk until the commit step, which runs *after* the whole download sits in `.partial/`. During the fetch those bytes are not free. `test_free_space_counts_the_bytes_the_old_copy_frees` encodes the failing case exactly: 1.0 MB free + a 1.5 MB old book for a 2.0 MB download passes pre-flight; on a real disk audible-cli hits ENOSPC mid-fetch and the job fails as a download error, not `disk_space`, after the user waited for it. The old book survives (B14 holds), so no loss — but the pre-flight no longer does its job for the one case F10 was about. F10's premise (clear before fetch) was removed by F7. **Fix:** count only the abandoned `.partial/` (it is `rmtree`'d before the fetch, so it is genuinely reclaimable) and drop the old-audio term; the peak for a re-download is old copy + 1.1× new, and ARCHITECTURE should say that. Update the docstring, §4.3 step 1, and the two tests (the "old copy frees" test becomes "old copy does not count"). |
| F35 | M | backend (B14 + F6) | **The commit window is not cancel-safe.** Between `_clear_local(target_dir)` and `os.replace(staged_audio, final)` (`download.py:796–804`) a SIGTERM raises `Cancelled` from `_sigterm_cancels._raise`; the `finally` then `_rmtree(partial)`, which still holds the staged audio. Old copy gone, new copy gone — the loss B14 exists to prevent, and the docstring promises "never costs the user a playable book". The window is four renames and a `write_meta`, so it is rare, but the UI's cancel-then-kill path (F6) makes a late SIGTERM plausible. **Fix:** block SIGTERM for the commit (`signal.pthread_sigmask(SIG_BLOCK, {SIGTERM})` before `_clear_local`, unblock after `write_meta`); a signal that lands in the window is delivered after the book is whole. A cancel that arrives after the commit should then count as success (the book is local), not `cancelled`. Lands naturally with F6 in **B12**, same handler. Test: monkeypatch `os.replace` to raise `Cancelled` on the audio move and assert a playable copy is still there. |
| F36 | L | Hopebox (H1) | **`ruff format --check .` fails on `main`.** #63 formatted `backend/`, `tests/` and `bin/omarchy-audible`, not `spikes/` (7 files). ## 3. Checked and fine (so nobody re-checks)

- No key in argv anywhere: `play_info` carries it in NDJSON, the player passes it as a `loadfile` option over the socket.
- `BackendCall.emitRecords` clears `lavf_options` on the same object `Ndjson.feed` pushed to `splitter.events`, after the synchronous `record` dispatch, so the outcome's event list never carries it. `Mpv.loadOptions` copies the string, so clearing the record does not touch `pendingLoad`.
- `EventLog.redactOptions` runs on every record before `logEvent`, at any depth; the only unredacted copy of the key between reply and `loadfile` is `pendingLoad.options.lavf`, which `giveUp()`, `quit()` and `flushPending()` all null.
- Reattach after a shell restart sends `clearKeyCommand` before `flushPending`.
- `removeBook` nulls the request and `pendingResume` for that book, and `busyAsins()` includes the request's book, so `flushRemovals` cannot remove under a load that is still on its way.
- B14 commit order (key, chapters, audio last, then meta) means "local" flips on the audio rename; `local_audio_file` needs `key.json` beside a locked file, and it is already there.
- #63 is mechanical for everything it touched.
